# 运营商绑定与认证生效

## 请求与状态

自助服务通过 `http://zfw.njupt.edu.cn:8080/Self/service/bind-operator` 修改运营商关系。移动账号、密码对应 `FLDEXTRA3/4`，电信对应 `FLDEXTRA1/2`。提交后，`service/operatorId` 表单提供当前管理端绑定值。

上网认证通过 p 的 `/eportal/portal/login` 提交校园账号、校园密码及运营商后缀，可明确选择 `801/802/803/804`：801、803 使用 HTTP，802、804 使用 HTTPS。管理端绑定读回与门户接受认证是两个观察点。

## 两种状态的生效边界

Self 表单读回正确表示管理端已保存绑定。p 仍可能返回“未绑定运营商账号,请正确绑定运营商账号再试！”，表示该次认证尚未使用到新关系。重新建立管理会话或执行 `dashboard/refreshaccount` 后，管理端可以继续读回同一绑定，而门户仍返回上述拒绝。

绑定提交还观察到另一种状态：POST 等待响应头超时，重新查询表单却已得到提交后的绑定。HTTP 提交结果与管理端字段读回因此分别记录；响应缺失时，内核返回 `unknown`，后续调用读取当前状态后再决定下一步。

因此，管理端字段与上网认证分别确认：先检查 Self 的目标账号、密码和另一运营商字段，再以 p 的认证结果及在线身份判断终端是否完成登录。

## 单独迁移与在线会话

独立迁移实验只执行旧账号解绑、目标账号绑定及各自读回，再按相同方式迁回原账号。实验期间持续读取门户状态，并通过绑定校园物理网卡的 HTTP 请求检查外网；上网注销、连接清退和门户认证均留在独立实验中。

绑定修改得到接受与准确读回，选定运营商的账号、密码符合各阶段目标，另一运营商字段保持原值。迁移与恢复时，门户的原账号及会话编号保持一致，校园物理连接的外网探测成功。

这个结果区分了两种操作：运营商改绑修改账号之间的管理关系；当前终端切换上网身份还需完成对应的门户认证。原会话在这次单独改绑中继续提供联网。

目标账号已经在线、目标宽带关系为空而同一宽带由另一校园账号持有的场景，也已通过登录脚本核对。脚本仅解除原关系并绑定目标账号，随后读取门户确认目标身份与 MAC；原会话编号保持一致，校园物理网卡的公网访问持续成功，认证次数为零。

## 离线后改绑与认证

受控实验先通过 Self 下线当前接入，确认在线记录消失、门户离线，以及校园物理网卡上的公网 HTTP 请求被重定向至门户。实验从宽带仍绑定原账号的状态开始，解除原绑定，再将同一宽带绑定至目标账号，并读回表单确认保存。

目标账号随即通过选定门户端口认证。认证侧先明确拒绝，提示“未绑定运营商账号,请正确绑定运营商账号再试！”，随后在绑定保持不变、使用同一端口的认证中接受请求，在线列表确认目标账号，校园物理网卡上的公网访问恢复。

该结果确认管理端保存绑定与认证侧使用新绑定不同步，也为登录脚本依据上述完整错误提示再次认证提供了实际依据。

## 正常上网时段的双向切换

正常上网时段，在同一接入链路和 801 端口完成两个校园账号之间的双向切换。两个方向均按当前账号下以 IP、MAC 唯一定位的 Self 连接下线，确认门户离线，再解除原绑定、绑定目标账号并认证。每次都从表单核对宽带账号与完整密码，另一运营商字段保持原值；门户返回目标账号与运营商，校园物理网卡的公网访问成功。

另一次实验保留已有宽带关系，精确清退当前连接，确认门户离线且校园物理网卡的公网 HTTP 请求返回门户重定向。随后一次原生 `p login` 即得到接受与在线身份确认，物理网卡公网访问恢复。这次登录没有重新绑定宽带。

重复验证时，在每次切换完成后持续观察目标账号的门户会话与物理网卡公网响应。观察期间各自会话编号保持不变，公网请求持续成功，最后恢复原账号及宽带关系。

双网卡改用自动接口度量值、TUN 保持启用后，再次完成同一往返流程。两个目标账号均通过 CLI 的同源外网探测和独立物理网卡 HTTP 检查；系统默认请求与本机代理请求也返回预期公网响应。持续观察中，各自门户会话与物理联网保持正常。

## 按认证结果决定等待

需要认证时，宽带绑定读回正确后立即提交认证。只有明确的 `rejected`、`verified:false` 与完整提示“未绑定运营商账号,请正确绑定运营商账号再试！”同时成立时，脚本才在设定的生效窗口内再次认证。收到完整拒绝便立即串行发起下一次认证，成功即继续。每次内核调用直接提交当前认证请求，接受后核对目标在线身份。

流程以认证结果确定何时结束等待。网络异常、未知响应、其他拒绝及接受后未核验成功均保留原结果并结束本次流程。

## 登录流程

Windows 登录示例通过 CLI `session` 保留门户实例和各账号独立的管理会话。解绑与绑定各自提交后使用独立 GET 结果，精确核对目标账号、密码和另一运营商字段；POST 跳转取得的业务结果页即可用于这次确认。门户登录返回已经核验的在线状态，脚本直接核对目标身份。

门户身份与宽带关系分别判断：目标账号和运营商已经在线时，关系迁移完成后读取门户确认连接保持，实际离线时再认证；在线身份不同则先精确清退，再处理绑定和目标认证。身份与绑定都已符合目标时直接使用当前连接。

内核保留各接口的独立结果：绑定的 `verified` 确认管理端字段，登录的 `verified` 确认终端在线身份。`BindingTimeoutSeconds` 设置新绑定的生效窗口。已有绑定和已经正确在线的路径按当前状态继续。
