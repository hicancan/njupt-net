# MAC 列表的直接查询与字段

## 2026-10-08 观察

浏览器的“我的设备”页面使用 `GET /Self/service/getMacList` 获取列表。实际非空响应的 `rows` 每行包含五个字符串，依次为在线状态、十二位十六进制 MAC、终端类型、最近登录时间和最近 IP。在线状态为字符串 `"0"` 或 `"1"`，页面将 `"1"` 显示为在线。

公开格式示例：

```json
{"total":1,"rows":[["1","aabbccddeeff","#PC","2026-10-08 17:34:00","192.0.2.10"]]}
```

## 页面是否为前提

实验新建一个管理会话，完成账号密码登录后，先直接查询 `service/getMacList`，再读取 `service/myMac` 页面并用相同参数查询列表。第一次即返回有效非空列表，两次 JSON 完全相同。

因此，设备查询直接请求列表接口。MAC 解绑仍先读取 `myMac`，因为解绑请求使用该页面提供的 `ajaxCsrfToken`。

在研究环境中重现比较：

```text
uv run --locked python -m zfw.mac --source SOURCE_IPV4 --config ../config.json --account ACCOUNT_ALIAS --compare-initialization
```

Go 将线上字符串状态解析为公开模型的整数 `online`，协议测试使用实际的字符串格式，并检查错误字段类型。研究程序保留原始列用于与页面格式对照。

## 解绑前提与确认

解绑先读取专用页面令牌，再分页定位目标 MAC。已找到目标即可提交一次；确认目标原本不存在时，需要读完全部预期记录。分页期间核对总数、每页行数和 MAC 唯一性，前置查询失败时返回 `not_submitted`。

服务器明确接受后，再分页确认目标消失。明确拒绝或处理结果无法识别时，返回该次处理结果。提交响应与列表状态各自承担不同职责：前者说明服务器如何处理这次动作，后者确认明确接受后的绑定变化。
